화면 중앙에 맵에는 경보를 가질 수 있는 노드들과 링크들이 있어.
나는 이 경보들을 발생시킨 핵심 원인인 장애점, 즉 노드 또는 링크 추정을 위한 로직을 구현하려고 해.

아래 단계별 장애점 추정 로직을 반영해서 결과를 Json 문자열로 리턴해주는 코드를 만들어줘.
코드에 대한 가독성을 높이고 향후 유지보수를 쉽게 하기 위해 코드를 간단히 작성해줘.

### 로직 기본 순서: 
1. "화면 UI에서 좌측 하단 장애점 찾기 버튼 클릭" => FaultDashboardApp의 handleFaultAnalysis 함수 호출.
2. handleFaultAnalysis 함수는 FailurePointManager js 모듈를 통해 => 파이썬 infer_failure_point API를 호출.
=> 파이썬 InferFailurePoint 클래스의 인스턴스가 단계적으로 장애점 추정하고 결과를 Json으로 반환.
3. 결과 Json을 API로 전달 => FailurePointManager는 API에서 받은 Json을 파싱, 해당 장애점들을 웹 ui 맵에서 애니메이션 처리, 채팅창에 장애점 추론 결과 요약 제공.

### 각 모듈과 함수의 역할/순서:
1. handleFaultAnalysis: FailurePointManager의 함수 호출, 2가지 파라미터 전달(현재 맵에 있는 노드들과 링크들의 전체 연결 정보, 전체 경보 정보).
2. FailurePointManager: 싱글톤 모듈 생성, infer_failure_point API를 POST로 호출, 위 1번의 2가지 파라미터를 그대로 다시 전달.
3. infer_failure_point API: routes.py에 API 생성, InferFailurePoint 인스턴스를 생성하여 함수 호출 파라미터를 그대로 다시 전달
4. InferFailurePoint: 아래 단계적 로직을 실행하여 장애점 추정 노드나 링크를 json 형태로 변환, API로 반환
5. infer_failure_point API: 다시 자신을 호출한 FailurePointManager에게 InferFailurePoint에서 받은 장애점 목록 json을 전달
6. FailurePointManager: infer_failure_point API에서 받은 json을 파싱하여 장애점에 해당하는 링크와 노드를 확인하여 웹 UI에 있는 맵에서 해당 노드와 링크에를 애니매이션 처리(외곽선을 빨간색으로 두껍게와 얇게로 계속 애니메이션).

### 단계별 장애점 추정 로직(장애점은 여러 개 일 수 있음):
1. 링크 장애점 판단: 전달받은 파라미터의 링크 중에서 경보가 있는지 여부 체크하여 경보가 있으면 장애점 링크로 판단("선로 피해 발생")
2. 상위 노드 장애점 판단: 경보가 있는 노드들 중에서 자신의 하위에 있는 모든 노드가 경보가 있으면, 다시 자신의 상위노드에 경보가 있는지 확인해서 상위 노드에 경보가 없으면 자신을 장애점으로 판단하고, 만약 상위 노드에도 경보가 있으면 상위 장비에 속한 모든 하위 노드에 경보가 있는지 확인해서 모든 하위 노드에 경보가 있으면 다시 다음 상위 노드들을 추적하며 해당 노드의 하위 노드들이 모두 경보가 있는지 판단하여 최종 상위 노드 장애점을 추적("상위 노드 장애점 추정").
3. 교환 노드 장애점 판단: 교환 분야 노드인 경우
3-1: 교환 A1935 장애판단: 교환 노드들이 "A1935" 경보가 100개 이상이면, 해당 교환 노드를 장애점으로 추정(“CGW 및 CGW 연동장비 체크 필요”).
3-2: 교환 A1930 장애판단: 다른 분야의 모든 노드들에 경보가 없고, 특정 교환 노드에 "A1930" 경보가 10개 이하 존재하는 경우 해당 교환 노드를 장애점으로 추정("AGW 단독고장으로 공통부 확인 필요").
3-3: IP와 전송 분야 노드들 중 경보가 있고, 특정 교환 노드에 "A1930" 경보가 11개 이상 존재하는 경우 교환 노드와 연결된 상위의 노드들 중 경보가 있는 교환 노드를 장애점으로 추정("AGW 단독고장으로 공통부 확인 필요").
4. 전송 노드 장애점 판단: 전송 분야 노드인 경우
4.1: 전송 LOS 장애판단: 전송 노드들 중 LOS 경보가 있으면, 상위에 있는 전송 노드와 링크를 장애점으로 추정("대항국 장비 장애 또는 광선로 단선").
4.2: 전송 LOF 장애판단: 전송 노드들 중 LOF 경보가 있으면, 상위에 있는 전송 노드를 전송 장애점으로 추정("대항국 장비 불량").

전송분야 Rule base
----------------------------------
ㅇ LOS 경보 : 광신호 혹은 전기적 신호가 손실되어 입력 신호가 없는 것으로, 근원적인 장애점은 99%의 확률로 대항국 장비나 광선로 단선으로 발생이 되며, 1%의 확률로 경보가 발생된 장치의 유니트나 광모듈 불량에 의해 발생됨.

ㅇ LOF 경보 : 광신호 혹은 전기적 신호가 손실되어 입력 프레임이 없는 것으로, 근원적인 장애점은 99%의 확률로 대항국 장비의 불량으로 발생이 되며, 1%의 확률로 경보가 발생된 장치의 유니트나 광모듈 불량에 의해 발생됨.

ㅇ AIS 경보 : LOS 경보, LOF 경보 발생시에 신호 진행방향으로 발생되는 경보로서 해당 경보는 무효 경보임.

ㅇ 1단계: 선로 경보가 있는 경우
----------------------------------
- 선로 장애 발생시 연결된 다른 모든 분야의 장비들도 다수 경보가 발생하며, 선로 피해로 인한 장애일 가능성이 높음.

ㅇ 2단계: MW(M/W, 마이크로 웨이브) 경보가 있는 경우
----------------------------------
- M/W의 전파 페이딩이나 M/W장비 자체의 장애일 가능성이 있으며, 연결된 다른 모든 분야 장비들도 다수 경보가 발생함.

ㅇ 3단계: 상위장비 경보가 있는 경우
----------------------------------
- 동일 분야의 상위장비가 경보가 발생하고, 추가로 동일 분야 하위 장비들이 모두 경보가 발생한 경우, 상위장비가 장애점일 가능성이 높음.

ㅇ 4단계: 전송 분야 장애점 판단 (경보패턴 분석: LOS, LOF)
----------------------------------
ㅇ LOS 경보 발생시, 광신호 혹은 전기적 신호가 손실되어 입력 신호가 없는 것으로 => 장애점은 99%의 확률로 대항국 장비나 광선로 단선으로 발생되어 장애점 가능성이 높음 (1%의 확률로 경보발생 장치의 유니트나 광모듈 불량도 가능).
ㅇ LOF 경보 발생시, 광신호 혹은 전기적 신호가 손실되어 입력 프레임이 없는 것으로 => 장애점 99%의 확률로 대항국 장비의 불량으로 발생되어 장애점 가능성이 높음 (1%의 확률로 경보발생 장치의 유니트나 광모듈 불량도 가능).

ㅇ 5단계: 교환 분야 장애점 판단 (경보패턴 분석: A1935, A1930)
----------------------------------
- A1935 경보 갯수가100개 이상 발생하면 유효한 경보이며, CGW 또는 CGW 연동장비 장애점 가능.
- A1930 경보가 1개 발생 시 다른 분야인 IP 분야 전송 분야 장비에서 경보 없으면 AGW 단독고장으로 공통부 장애점 가능.
- A1930 경보가 10개 이상 다량 발생일 경우, 다른 분야인 IP 분야 전송 분야 장비에서도 경보가 발생한 경우 해당 IP 분야나 전송 분야 장비 시스템 장애 또는 연결된 상위 장비가 장애점 가능.

ㅇ 6단계: IP 분야 장애점 판단 (Critical, Major, SNMP OperStatus 경보 체크)
----------------------------------
- syslog(시스로그) 경보 등급이 'M' 또는 'C'인 경우(M: Major, C: Critical 경보) 해당 장비가 장애점 가능.
- 장비가 '대용량 OLT', '주중계, 'MNP', '신인증 SER'이고, 경보 메시지에 'SNMP OperStatus'가 포함되어 있으며

ㅇ 7단계: 무선 분야 장애점 판단 (경보패턴 분석: NE3S, ToP, BTS)
----------------------------------
- 경보 메시지에 “Timeout connecting to NE3S” 경보가 포함된 경우
=> 동시간대인 최근 10분 내 경보가 10개 이상 다량 발생하고, 추가로 직접 연결된 IP 또는 전송 분야 장비에서도 경보 발생 시 => 광케이블 선로 장애 또는 상위망(무선 백본) 장애 가능.

- 경보 메시지에 “ToP reference missing, BTS reference clock missing” 경보가 포함된 경우.
=> 동시간대인 최근 10분 내 경보 10개 이상 다량 발생하고, 추가로 직접 연결된 IP 또는 전송 분야 장비에서도 경보 발생 시 => 광케이블 장애 또는 상위망(무선 백본) 장애 가능.
=> 동시간대인 최근 10분 내 경보 10개 이상 다량 발생했으나, 그러나 직접 연결된 IP 또는 전송 분야 장비는 경보가 없을 때 => ToP(클럭공급장치) 장애 가능.

MW 분야 경보분석 및 장애판단 기준
######################
✅ 1. 페이딩(Fading) 판단
지표	기준값	해석
TSL	-5 ~ -10 dBm (정상 범위)	송신 전력 정상
RSL	-85 dBm 이하 (급감)	수신 신호 약해짐
SNR	< 10 dB	신호 품질 급락
XPI	-28 dB 이하 (정상)	편파 간섭 없음
ERR	0~2% (약간 증가 가능)	전송 오류 생길 수 있음

🟡 요약 조건: TSL 유지, RSL 급하락, SNR 동반 하락
→ 전형적인 일시적 또는 주기적 페이딩 의심

✅ 2. 안테나 정렬과 편파 판단
지표	기준값	해석
TSL	-5 ~ -10 dBm	송신 정상
RSL	-80 ~ -90 dBm	낮지만 급격하진 않음
SNR	> 10 dB	수신 품질은 유지됨
XPI	-22 dB 이상 (나쁨)	편파 정렬 문제
ERR	0 ~ 1%	가벼운 오류 가능
🟡 요약 조건: RSL은 조금 낮지만, SNR은 정상 범위, XPI 수치 나쁠 때
→ 안테나 정렬 불량, 편파 불일치 가능성 높음

✅ 3. MW 장비 이상 또는 전원 문제
지표	기준값	해석
TSL	< -15 dBm (너무 낮음)	송신 이상
RSL	-90 dBm 이하	수신 약함
SNR	< 10 dB	품질 저하
XPI	-25 ~ -30 dB	보통 또는 나쁨
ERR	> 2~3%	전송 오류 증가
🟡 요약 조건: TSL 자체가 낮거나 흔들림, 나머지 지표도 나쁘면 
→ 장비 고장, RF 회로 이상, 전원 공급 불량 가능성 높음

✅ 4. 간섭 또는 고주파 혼선
지표	기준값	해석
TSL	-5 ~ -10 dBm	정상
RSL	-65 ~ -75 dBm	양호
SNR	< 10 dB	잡음/간섭 심함
XPI	-25 dB 이상	편파 혼선 의심
ERR	1 ~ 5%	혼선에 의한 전송 오류 가능성 ↑
🟡 요약 조건: RSL은 정상, SNR과 XPI 나쁠 때
→ 외부 간섭이나 혼선 (Interference) 가능성 높음

🎯 전체 비교 요약표
원인	TSL	RSL	SNR	XPI	ERR
페이딩	✅ -5~-10	❌ -85↓	❌ <10	✅ 정상 (-30↓)	⚠︎ 약간 상승
안테나 정렬 불량	✅ 정상	⚠︎ -85 정도	✅ >10	❌ -22↑	⚠︎ 낮음
장비 이상	❌ < -15	❌ -90↓	❌ <10	❌ 보통	❌ >2~3%
간섭/혼선	✅ 정상	✅ -70	❌ <10	❌ -25↑	⚠︎ 상승 가능

MW 장애점 판단 로직 수정
------------------------------------
✅ 1. 페이딩(Fading) 판단 로직 개선
- 기존: 임계치 기반 단순 비교
- 개선: TSL 유지(-5~-10dBm) + RSL 급하락(-85dBm↓) + SNR 동반 하락(<10dB) 조건

✅ 2. 새로운 MW 장애 판단 로직 추가
  2-1. 안테나 정렬과 편파 판단
  => TSL 정상(-5~-10dBm) + RSL 조금 낮음(-80~-90dBm) + SNR 정상(>10dB) + XPI 불량(-22dB↑)
  2-2. MW 장비 이상 또는 전원 문제
  => TSL 너무 낮음(<-15dBm) + RSL 매우 낮음(-90dBm↓) + SNR 불량(<10dB) + ERR 높음(>2%)
  2-3. 간섭 또는 고주파 혼선
  => TSL 정상(-5~-10dBm) + RSL 양호(-65~-75dBm) + SNR 불량(<10dB) + XPI 불량(-25dB↑)

✅ 3. 기존 로직 유지
  ERR 파라미터 체크: 기존 로직 그대로 유지
  전압 기준 한전 정전: 42V 임계치 기준 그대로 유지

✅ 4. 분석 과정 개선
  각 슬롯별로 5가지 장애 유형을 순차 분석
  장애점 생성 시 모든 유형 통합 처리
  상태 요약에 6개 항목 표시 (페이딩/안테나/장비/간섭/전파수신/전원)

1. Microwave 전송 장애 판단 기준 (ERR 유형별)
------------------------------------
다음 표는 ERR 항목별로 어떤 조건일 때 장애로 판단하는지, 그리고 일반적인 원인을 함께 정리한 것입니다.

항목	정상 기준	장애 판단 기준	해석 및 주요 원인
BER
(Bit Error Rate)	0 또는 순간적 수 건
(10건 미만, 일시적)	✅ 지속적 오류 발생
✅ 10분 내 100건 이상
✅ 누적적 증가 추세	- 순간적 간섭
- 전송로 품질 저하
- RF 간섭 (5G, Wi-Fi 등)
ES
(Errored Seconds)	0	✅ 10초 이상 오류 발생 시
(특히 연속 발생)	- 링크 품질 불안정
- 간헐적 페이딩
- 편파 정렬 불량
SES
(Severely Errored Seconds)	0	✅ 5초 이상 SES 발생 시
(특히 1시간 내 반복 시)	- 심각한 전송 품질 저하
- 급격한 페이딩
- RF 출력 문제
UAS
(Unavailable Seconds)	0	✅ 1초 이상이면 장애로 판단
→ 링크 자체가 사용 불가 상태였음을 의미	▶︎ 아래 UAS 원인 설명 참고
BBE
(Background Block Errors)	0~몇 건 (일시적 허용)	✅ 지속적 증가
✅ 1분 내 100건 이상 또는 10분간 계속 발생	- 전송로 블록 오류 누적
- FEC 동작 구간 돌입
- 간섭/정렬/장비 이상 등 다양한 원인 가능
✅: 장애 알람 발생 기준 (통신사 운영 정책에 따라 수치 약간 달라질 수 있음)


UAS (Unavailable Seconds) > 0 의 의미 및 원인
UAS > 0이라는 것은 Microwave 링크가 일정 시간 이상 “사용 불가(Unavailable)” 상태였음을 의미합니다.

이건 단순한 오류보다 더 심각하며, 아래처럼 물리/환경/장비 문제를 포함한 근본 원인이 수반됩니다.

🚨 UAS 발생 가능한 주요 원인 유형
------------------------------------
원인 유형	세부 설명
🔌 전원 차단 / 케이블 단선	- IDU/ODU 전원 불안정
- 파워 서플라이 이탈 또는 리부팅
- 전송 장비 자체 Down
📡 전파 경로 손실 (페이딩)	- 심한 강수, 안개, 눈, 태풍 등
- 주간 일조/야간 냉각에 따른 다중경로 페이딩
- 갑작스러운 RSL 급하락 + SNR 저하와 동반
🚧 장애물 발생 (Blockage)	- 크레인, 대형 트럭, 신규 건축물로 LOS(Line of Sight) 차단
- 이동식 구조물 간섭
🎛 장비 리부팅 또는 설정 변경	- 펌웨어 업그레이드
- 라우팅/스위칭 구성 중단
- IDU/ODU 간 링크 재협상 중
🧯 장비 고장 또는 포트 불량	- Tx/Rx 포트 접촉 불량
- RF 모듈 손상
- IF 케이블 손상
🔄 장비 간 프로토콜 Sync 실패	- Ethernet/SDH/PDH 신호 불일치
- 장비 간 시계(Sync) 불일치로 인한 링크 낙하


✅ 장애 판단 기준 요약 (항목별)
------------------------------------
항목	장애 기준	해석
BER	> 20 → 장애 / 1~20 → 경미한 오류 / 0  정상	=> 순간적인 오류는 무시 가능. 누적되면 문제
ES	≥ 10 → 장애 / 1~9 → 경고 수준 => 오류 초 발생 수

2. Microwave 전송 장애 판단 기준 (ERR 유형별)

🔍 주요 수정 필요 사항
1. SNR 기준값 재검토 필요
현재 제시된 기준: SNR < 10dB => 문제점: 너무 낮은 기준값
권장 기준:
정상: SNR > 25dB
경고: SNR 15~25dB
장애: SNR < 15dB

2. XPI 표기 방식 통일 필요
현재 표기가 혼재됨

"-28dB 이하 (정상)" vs "-22dB 이상 (나쁨)"
표준 표기법:
정상: XPI > 30dB (또는 < -30dB로 표기 시)
경고: XPI 20~30dB
장애: XPI < 20dB

3. RSL 기준값 세분화 필요
링크 설계에 따라 달라짐

일반적 기준: 설계 RSL 대비 상대적 평가
절대값보다는 "설계값 대비 -5dB 이하" 같은 상대적 기준 권장

- ### 소켓통신 함수 샘플: zmp 라이브러리 사용.
2.4 InferFailurePoint에서 응답 json 값으로 'MW 장비 상태 점검' 장애점을 분석
- 장애점 판단 로직 1) 여러 slot 중 RSL, TSL, SNR, XPI => value 값이 min, max 범위를 벗어나거나, threshold보다 적으면 '전파 페이딩 의심'으로 판단.
- 장애점 판단 로직 2) ERR가 1개라도 있으면 '수신 오류로 페이딩이나 대국 장비 장애 의심'으로 판단
- 장애점 판단 로직 3) VOLT => value 값이 min, max 범위를 벗어나거나, threshold보다 적으면 '배터리 모드로 한전 정전 의심'으로 판단.

# AI RAG 장애분석 팝업 API 엔드포인트 추가
# 장애분석 팝업 화면 렌더링
@api_bp.route("/check_mw_status", methods=["POST"])
def check_mw_status():
    try:
        # 요청 데이터 검증
        if not request.is_json:
            return jsonify({
                'success': False,
                'error': 'Content-Type이 application/json이어야 합니다.'
            }), 400

        data = request.get_json()
        if not data:
            return jsonify({
                'success': False,
                'error': '요청 데이터가 없습니다.'
            }), 400

        guksa_id = data.get('guksa_id')
        equipment_list = data.get('data', [])

        if not equipment_list:
            return jsonify({
                'success': False,
                'error': 'MW 장비 데이터가 없습니다.'
            }), 400

        logging.info(
            f">> MW 상태 확인 요청: 국사={guksa_id}, 장비 수={len(equipment_list)}개")

        # 소켓 서버로 요청
        payload = {
            "guksa_id": guksa_id,
            "data": equipment_list
        }

        # 재시도 로직 구현 (개선됨)
        max_retries = 2  # 재시도 횟수 2회
        timeout_ms = 2000  # 2초로 단축
        context = None
        socket = None

        try:
            context = zmq.Context()

            for attempt in range(max_retries):
                try:
                    start_time = time.time()
                    logging.info(f">> MW 상태 확인 시도 {attempt + 1}/{max_retries}")

                    # 재시도 시 기존 소켓이 있으면 닫기
                    if socket:
                        socket.close()

                    # ZMQ 소켓 연결 및 요청 (타임아웃 최적화)
                    socket = context.socket(zmq.REQ)

                    # 모든 타임아웃 설정 (밀리초 단위)
                    socket.setsockopt(zmq.RCVTIMEO, timeout_ms)    # 수신 타임아웃
                    socket.setsockopt(zmq.SNDTIMEO, timeout_ms)    # 송신 타임아웃
                    # 소켓 종료 시 즉시 닫기
                    socket.setsockopt(zmq.LINGER, 0)

                    # 연결 시도
                    socket.connect(MW_SOCKET_SERVER)

                    # 요청 전송
                    logging.debug(
                        f"요청 JSON: {json.dumps(payload, ensure_ascii=False)}")
                    socket.send_string(json.dumps(payload))
                    logging.info(
                        f">> 소켓 서버로 MW 상태 요청 전송: {len(equipment_list)}개 장비")

                    # 응답 수신
                    response_str = socket.recv_string()
                    logging.debug(f"응답 JSON: {response_str}")

                    # JSON 파싱
                    response_data = json.loads(response_str)
                    elapsed_time = time.time() - start_time
                    logging.info(
                        f"소켓 서버로부터 MW 상태 응답 수신 완료 (시도 {attempt + 1}, {elapsed_time:.2f}초)")

                    return jsonify(response_data), 200

                except zmq.error.Again:
                    elapsed_time = time.time() - start_time
                    logging.warning(
                        f"소켓 서버 응답 타임아웃 (시도 {attempt + 1}/{max_retries}, {elapsed_time:.2f}초)")
                    if attempt == max_retries - 1:  # 마지막 시도
                        logging.error("모든 재시도 실패: 소켓 서버 응답 타임아웃")
                        return jsonify({
                            'success': False,
                            'error': f'소켓 서버 응답 타임아웃 ({max_retries}회 시도 후 실패)'
                        }), 408

                except zmq.error.ZMQError as zmq_error:
                    elapsed_time = time.time() - start_time
                    logging.warning(
                        f"ZMQ 오류 (시도 {attempt + 1}/{max_retries}, {elapsed_time:.2f}초): {str(zmq_error)}")
                    if attempt == max_retries - 1:
                        logging.error(f"모든 재시도 실패: ZMQ 오류: {str(zmq_error)}")
                        return jsonify({
                            'success': False,
                            'error': f'소켓 서버 통신 실패: {str(zmq_error)} ({max_retries}회 시도 후 실패)'
                        }), 500

                except Exception as socket_error:
                    elapsed_time = time.time() - start_time
                    logging.warning(
                        f"소켓 통신 오류 (시도 {attempt + 1}/{max_retries}, {elapsed_time:.2f}초): {str(socket_error)}")
                    if attempt == max_retries - 1:  # 마지막 시도
                        logging.error(
                            f"모든 재시도 실패: 소켓 통신 오류: {str(socket_error)}")
                        return jsonify({
                            'success': False,
                            'error': f'소켓 서버 통신 실패: {str(socket_error)} ({max_retries}회 시도 후 실패)'
                        }), 500

        except Exception as e:
            logging.error(f"소켓 통신 초기화 오류: {str(e)}")
            return jsonify({
                'success': False,
                'error': f'소켓 통신 초기화 실패: {str(e)}'
            }), 500

        finally:
            # 소켓과 컨텍스트 안전하게 정리
            try:
                if socket:
                    socket.close()
                    logging.debug("소켓 연결 종료")
                if context:
                    context.term()
                    logging.debug("ZMQ 컨텍스트 종료")
            except Exception as cleanup_error:
                logging.warning(f"소켓 정리 중 오류: {str(cleanup_error)}")

    except Exception as e:
        error_message = f"MW 상태 확인 중 오류 발생: {str(e)}"
        logging.error(error_message)
        logging.error(traceback.format_exc())

        return jsonify({
            'success': False,
            'error': error_message
        }), 500
